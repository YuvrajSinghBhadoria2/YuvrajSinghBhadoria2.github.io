Speculative Decoding Is Broken Under JSON Schemas — Here's the Fix

84.9% of speculative drafts get thrown away when output must match a grammar. Masking the drafter's logits turns the standard throughput lever back on — measured end-to-end, dead ends included.

Yuvraj Singh Bhadoria·October 17, 2026·9 min read

Every AI agent you ship runs on JSON. Tool calls, structured outputs, schema-constrained decoding — that's the workload. And speculative decoding, the standard throughput lever for LLM serving, quietly falls apart on exactly that workload. I measured it, root-caused it, and fixed it. This post covers the whole path — including the three dead ends that shaped the final design.

01 · The ProblemDrafts can't read the rulebook

Speculative decoding drafts tokens cheaply with a small drafter, then verifies them against the target model in one batched forward pass. Under grammar-constrained decoding, the verifier only accepts grammar-valid tokens — but the drafter knows nothing about the grammar.

vLLM masks at verification only. The draft step is where 84.9% of the waste happens — that's where this fix goes.

Measured with vLLM 0.11.2 + xgrammar + Qwen2.5-7B on an A100: under a JSON schema, 84.9% of n-gram drafts were rejected by the grammar FSM (292 of 344). Unmasked EAGLE3 — the strongest drafter vLLM supports — accepted only 1.44 tokens per propose call on agentic JSON and ran 0.97× slower than no speculation at all. Spec decode wasn't unhelpful here; it was a pessimization.

This isn't a niche corner: vLLM's Q4 2026 roadmap carries the open item “Improve configuration ergonomics and robustness with tool calling, reasoning, and structured outputs.”

02 · Three Dead EndsWhy the obvious fixes don't work

I kept every negative result — they're what makes the final design make sense.

  • Truncate invalid drafts.rejected — 0.24× Valid output, but draft length collapses. There's nothing left to speculate on.
  • Replace invalid drafts with the first bitmask-valid token.rejected — valid ≠ likely 83.1% of drafts got substituted and were rejected at verification anyway. The verifier wants what the model would actually say.
  • Run a small standalone drafter with masked logits inside propose().rejected — 61× slower Correct architecture on paper, 183.5 ms vs 13.5 ms per token in practice — a second forward pass inside the sampling loop serializes everything.
The lessonThe fix has to live inside the shared forward pass, at the point where draft logits already exist — not beside it, and not after the fact.

03 · The FixMask the draft's logits, not just the target's

vLLM's EAGLE3 path computes draft logits and immediately argmaxes them. The head's logits are scattered into the target's vocabulary space before that argmax — which means a standard xgrammar bitmask applies directly, at every speculative position:

# inside EagleProposer.propose(), per draft position
logits = self.model.compute_logits(hidden, attn)   # target vocab
apply_token_bitmask_inplace(logits, bitmask)     # ← insert here
token = logits.argmax(dim=-1)

The mask needs grammar state that advances with each drafted token. The final design builds a fresh GrammarMatcher per propose call, replays the committed-token history into it, masks all K draft positions, then discards it — zero rollback() calls. Why not reuse one matcher and roll back the drafted-but-rejected window: xgrammar 0.1.25's rollback() desynced after a permanent accepted prefix when the window held forced-continuation tokens (e.g. char-splatted enum values). The matcher returns without error but stops reflecting the true grammar state.

If the draft-vocab subset contains no grammar-valid token for a row, the fallback takes the first grammar-valid token. Measured fallback rate: 0 of 4,486 masks.

Unexpected findingConstrained spec decode degrades output validity on hard schemas — unmasked EAGLE3 produced 3/8 valid outputs vs 5/8 for no-spec, pushed into degeneration loops until the token cap. Grammar-masking the drafts restores validity to the no-spec level (5/8) while also being the fastest configuration. And the acceptance boost is larger on the schema with more enums (+50.2% vs +36.5%) — enums are exactly where unconstrained drafts wander off.

05 · TakeawaysWhat I'd tell a serving team tomorrow

Grammar-valid is not model-likely — and model-likely is not grammar-valid. Under constrained sampling, speculative decoding needs both, at the draft step, where it's cheap.
  • The problem is real and large: 84.9% of n-gram drafts are grammar-invalid under a JSON schema.
  • Grammar-valid ≠ model-likely: first-valid-token substitution gets rejected anyway (83.1% substituted → still rejected).
  • A drafter must share the target's forward pass: a standalone drafter inside propose() is 61× slower.
  • Masking after the d2t scatter flips the economics: a net-negative speculative config (0.967× vs no-spec) becomes net-positive (1.154×).
  • Harder schema → larger acceptance win (+36.5% → +50.2%) — enums are where drafts wander off.
  • Constrained spec decode can degrade validity; grammar-masking the drafts restores it.

The prototype is a monkey-patched EagleProposer — the shape of a real vLLM change is clear: a bitmask hook in the draft loop plus a per-request matcher lifecycle. I've filed it upstream as a design issue on vLLM. Open questions I'd like to push on: batch > 1, a GPU-resident FSM to remove the remaining per-position host sync, and whether the same idea transfers to MTP heads.
